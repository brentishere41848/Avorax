# Checkpoint 2208: Authenticode Low-Integrity Primary Token

Reduce the release Authenticode helper's authority during the trust-provider
phase that cannot run under checkpoint 2205's `WRITE_RESTRICTED` impersonation

Integrity before `CreateProcessAsUserW`. Require bounded parent and child

## Security Design

The parent opens its token with the existing query/duplicate/assign rights plus
`TOKEN_ADJUST_DEFAULT`, creates the existing `DISABLE_MAX_PRIVILEGE` restricted
primary token, and then calls `SetTokenInformation(TokenIntegrityLevel)` with a
bounded, validated `TOKEN_MANDATORY_LABEL` whose SID is generated by
`CreateWellKnownSid(WinLowLabelSid)`. The setter uses `SE_GROUP_INTEGRITY` as
the documented input attribute. Read-back accepts only that mandatory integrity
bit plus Windows' optional canonical `SE_GROUP_INTEGRITY_ENABLED` bit, rejects
every unrelated attribute, and byte-compares the returned SID with a fresh
validated `WinLowLabelSid`.

The common bounded SID parser checks that the returned pointer, SID header,
subauthority-derived length, and complete SID all remain inside the exact
`GetTokenInformation` byte count before `IsValidSid`, `GetLengthSid`, or byte
copy. Parent validation occurs before `CreateProcessAsUserW`. The child repeats
type, privilege, integrity SID, and attribute validation before process
mitigation read-back, stdin, JSON parsing, candidate access, WinTrust, catalog,
hash, or response work. There is no inherited-integrity or weaker-launch retry.

Windows Mandatory Integrity Control evaluates no-write-up before the DACL. A
low-integrity process therefore cannot write an ordinary medium-integrity or
unlabelled object even when the same user SID is granted by the DACL. A benign
child regression explicitly calls `RevertToSelf`, reads and hashes a temporary
medium-integrity text file, receives access denied for a write open, and proves
the file stayed unchanged. This demonstrates that same-process reversion can
return only to the low-integrity primary token.

## Limits

Low Mandatory Integrity is not identity separation. The helper keeps the parent
user SID, profile and registry namespace, desktop, ordinary read access, and
the three intentional stdio handles. It is not an AppContainer, LPAC, separate
desktop, authenticated cross-identity IPC channel, or denial of writes to
objects explicitly labelled to permit low-integrity mutation.

The primary token remains not `WRITE_RESTRICTED` because the verified Windows
loader failed with `0xC0000142` under that primary-token policy. WinTrust and
catalog work still run under the primary token because the trust stack failed
with error `127` under the write-restricted impersonation token; this checkpoint
requires that primary token to remain low integrity. Mandatory Integrity Control
does not constrain already mapped executable/non-image data, existing writable
mappings, or mutation after the verdict. Installed LocalSystem compatibility,
third-party trust providers, production signing, signed-driver enforcement,
pre-execution blocking, Defender replacement, and production accuracy remain
partial, blocked, or technically limited.

## Dependency And Safety

The implementation reuses pinned `windows-sys 0.61.2` bindings already enabled
by `Win32_Security` and `Win32_System_SystemServices`; it adds no crate, package,
Cargo feature, build script, network fetch, license, or lockfile change. Tests
use only ignored benign Rust child fixtures, installed read-only Microsoft
binaries, and temporary benign text. Candidate fixtures are never executed.
No live malware, download, installation, service/driver start, Defender change,
release, publication, or protected-quarantine mutation is permitted.
